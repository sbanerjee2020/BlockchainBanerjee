Quantum-Proofing Ethereum

A quantum computer running Shor's algorithm would read anyone's private key straight off their public key. Here is exactly which of Ethereum's building blocks that breaks, which survive, and the arithmetic — worked out by hand, in full — behind each one.

01 — Why any of this is necessary

A lock that quantum computers can pick

Every Ethereum account is protected by a one-way function: a calculation that's cheap to run forward and, with today's computers, unreasonably expensive to reverse. Your private key is a number; your public key is what you get after doing math to it that's easy in one direction only. Sign a transaction and you prove you know the private key, without revealing it — because reversing the math to find it would take longer than the universe has existed.

Ethereum uses two flavors of this: ECDSA over secp256k1 for ordinary accounts (EOAs), and BLS signatures for the roughly 1 million validators who run consensus. Both rely on the same underlying hard problem — the discrete logarithm problem on an elliptic curve.

Worked example — the one-way function itself
Pick a small stand-in world: numbers mod 97, with generator g = 5
Forward (easy — this is what signing/verifying does):
secret exponent x = 55 -> compute 5^55 mod 97
by repeated squaring: 5^1=5, 5^2=25, 5^4=43, 5^8=6, 5^16=36, 5^32=35 ...
5^55 mod 97 = 5^32 x 5^16 x 5^4 x 5^2 x 5^1 mod 97 = 57 ✓ five multiplications
Backward (this is the private key, recovered from the public key):
given "57", find x such that 5^x mod 97 = 57
no shortcut exists but trying exponents — fine for mod 97, ruinous for a 256-bit modulus

Real Ethereum keys use a modulus with 78 digits, not 97. Trying every exponent classically would outlast the sun. But in 1994, Peter Shor showed a quantum computer can find that hidden exponent efficiently, using the quantum Fourier transform to detect a periodic pattern in the exponentiation that a classical computer can't see without brute force. Run Shor's algorithm on a public key, and the matching private key falls out — ECDSA and BLS are both this exact same math, so both fail simultaneously.

What doesn't break Hash functions (SHA-256, Keccak) aren't one-way trapdoors built on a hidden number — they're scrambling functions with no algebraic structure for Shor's algorithm to exploit. The only quantum speed-up against them is Grover's algorithm, which merely halves the effective security bits (searching the square root of the possibilities instead of all of them). Doubling the hash output size fixes that completely. This is why every post-quantum scheme below is built out of hash functions, not elliptic curves.

Timeline and what's actually at risk

Industry estimates put a cryptographically-relevant quantum computer — one with enough error-corrected qubits to actually run Shor's algorithm at this scale — in the early-to-mid 2030s, though qubit error-correction has repeatedly proven harder than roadmaps assumed. Two things are commonly misunderstood:

  • "Harvest now, decrypt later" is not the blockchain risk. That phrase describes encrypted data being captured today for decryption later — a confidentiality problem. A finalized Ethereum block is already public; there's nothing confidential to harvest. The real risk is forward-looking: forging a new signature for funds under a key that becomes crackable in the future.
  • Only exposed public keys are at risk. An address that has never sent a transaction has revealed only a hash of its public key, not the key itself. Ethereum's dormant, never-exposed supply is estimated at roughly 0.1% — much smaller than Bitcoin's equivalent legacy exposure.
02 — In production today quantum-vulnerable

KZG commitments

Since EIP-4844 ("blobs"), every rollup batch Ethereum stores is compressed using a KZG polynomial commitment. It's an elegant trick: turn a chunk of data into a single elliptic-curve point, small enough to put on-chain, that lets anyone later prove "byte #4,000 of this blob really was X" — without republishing the whole blob.

The idea, in one sentence

Treat your data as the coefficients of a polynomial. Committing to the polynomial is one point; proving any single value of it is one more point. Nobody needs to see the polynomial itself to check either.

Worked example — committing to a tiny "blob"
Blob = three numbers [3, 5, 2] -> polynomial p(x) = 3 + 5x + 2x^2
Trusted setup fixes a secret point s = 4 nobody — including the prover — knows in real life
(here we "peek" at s only to show the arithmetic; real KZG hides it inside an elliptic-curve point)
p(4) = 3 + 5(4) + 2(16) = 3 + 20 + 32 = 55
Commitment C = g^p(s) mod 97 = 5^55 mod 97 = 57 <- this single number is published on-chain

Later, a rollup wants to prove that p(2) = 21 — one specific value inside the blob — without revealing the other coefficients.

Worked example — proving one value without revealing the polynomial
Claim: p(2) = 3 + 5(2) + 2(4) = 3 + 10 + 8 = 21
Build the quotient q(x) = ( p(x) - 21 ) / ( x - 2 )
2x^2 + 5x - 18 divided by (x - 2) = 2x + 9 remainder 0 (exact division = the claim is true)
Proof pi = g^q(s) mod 97, q(4) = 2(4) + 9 = 17 -> pi = 5^17 mod 97 = 83
Verifier's check (in reality done via elliptic-curve pairing, never learning s):
p(s) - y ?= (s - 2) x q(s)
55 - 21 = 34 (4 - 2) x 17 = 34 ✓ identity holds

That final identity — checked as elliptic-curve points through a pairing function, so the verifier only ever sees C and pi, never s, p, or the raw blob — is the entire trust mechanism behind billions of dollars of rollup data today.

Why it doesn't survive Shor's algorithm Every step above is modular exponentiation and elliptic-curve pairing — exactly the discrete-log structure from Section 01. A quantum computer that breaks ECDSA breaks KZG's trapdoor the same way. KZG isn't on Ethereum's list of things to patch urgently — blob commitments are short-lived and pruned — but any long-term successor needs a hash-based replacement, which is exactly what Section 03 is.
03 — The post-quantum alternative hash-based

Zero-knowledge proofs, and why STARKs specifically

A zero-knowledge proof lets you convince someone a statement is true — "I ran this program correctly," "these 500,000 validator signatures are all valid" — without showing them the underlying data. Most zk-SNARKs (behind most zk-rollups today) get their succinctness from the same elliptic-curve pairings as KZG, inheriting the same quantum weakness. ZK-STARKs get succinctness a different way: purely from hash functions and polynomials, with no trusted setup and no elliptic curves — which is exactly why Ethereum's post-quantum plans lean on STARKs rather than SNARKs.

The core trick: check one random point instead of everything

If two low-degree polynomials agree at more random points than their degree, they are — overwhelmingly likely — the exact same polynomial everywhere (the Schwartz-Zippel lemma). So instead of re-checking a computation step by step, a STARK turns the whole execution trace into one polynomial and checks it at a small number of random points. The remaining piece is proving that polynomial really is low-degree, which is what FRI (Fast Reed-Solomon IOP) does, by repeatedly folding it in half.

Worked example — one round of FRI folding
Start: f(x) = 1 + 2x + 3x^2 + 4x^3 (degree 3 — stands in for a computation trace)
Split into even/odd coefficients:
f_even(y) = 1 + 3y f_odd(y) = 2 + 4y so that f(x) = f_even(x^2) + x . f_odd(x^2)
Verifier draws a random challenge r = 5 and the fold becomes:
f'(y) = f_even(y) + r . f_odd(y) = (1+3y) + 5(2+4y) = 11 + 23y <- degree halved: 3 -> 1
Worked example — the verifier's spot-check, using only two openings
Prover has committed to f via a Merkle tree of its values (hashes only — no curves)
Verifier queries two paired points, x = 2 and x = -2:
f(2) = 1 + 4 + 12 + 32 = 49
f(-2) = 1 - 4 + 12 - 32 = -23
Verifier reconstructs, without ever seeing the coefficients directly:
f_even(4) = ( f(2) + f(-2) ) / 2 = ( 49 - 23 ) / 2 = 13
f_odd(4) = ( f(2) - f(-2) ) / 4 = ( 49 + 23 ) / 4 = 18
Combine with the same challenge r = 5 and compare to the prover's next-round commitment:
f'(4) = 13 + 5(18) = 103 ✓ matches — one query, whole round verified
Each round halves the degree with one random challenge; a handful of rounds collapse a huge trace into a proof a few kilobytes long.

This is the machinery underneath both zk-rollup provers built on STARKs and — as Section 05 covers — Ethereum's plan for compressing thousands of post-quantum validator signatures into one small proof.

04 — Replacing the keys themselves hash-based

Hash-based signatures: leanSig and XMSS

If elliptic-curve signatures are out, what replaces them has to be built from something Grover's algorithm can't meaningfully weaken: hash functions. The oldest idea here, Lamport's one-time signature, is almost embarrassingly simple.

Step 1 — a signature you can use exactly once

Pick two secret numbers, one for "the message bit is 0" and one for "the message bit is 1." Publish only their hashes. To sign, reveal the secret that matches your actual bit — the verifier hashes it and checks it matches the public value you already published.

Worked example — a one-time signature (toy hash h(x) = x^2 + 7 mod 101)
Secret key: sk0 = 23 sk1 = 59
Public key: pk0 = h(23) = 23^2+7 = 536 mod 101 = 31
pk1 = h(59) = 59^2+7 = 3488 mod 101 = 54
To sign bit = 1: reveal sk1 = 59 (sk0 stays secret forever)
Verifier computes h(59) = 54 and checks it against the published pk1 = 54 ✓ valid

Notice the catch in the name: one-time. Sign a second, different message with the same key pair and you'd reveal enough hash preimages that an attacker could forge signatures for messages you never signed. A real scheme (WOTS+, used inside XMSS and Ethereum's leanSig) uses longer hash chains per bit to make this more compact, but the one-time limitation is structural, not a shortcut Ethereum is taking.

Step 2 — turning "one-time" into "one persistent public key"

You obviously can't hand every validator a brand-new public key for every signature. XMSS's fix: generate many one-time key pairs in advance, and hash them together into a Merkle tree. The tree root is your one long-term public key. Each signature reveals one leaf's secret plus the sibling hashes needed to recompute the root — proving that leaf really belongs to the published key, without exposing any other leaf.

Worked example — combining 4 one-time keys into one public key (toy hash h2(a,b) = 31a + 17b + 3 mod 101)
Leaves (one-time public keys): L1=31 L2=54 L3=77 L4=12
Node12 = h2(31, 54) = 31(31) + 17(54) + 3 = 1882 mod 101 = 64
Node34 = h2(77, 12) = 31(77) + 17(12) + 3 = 2594 mod 101 = 69
Root = h2(64, 69) = 31(64) + 17(69) + 3 = 3160 mod 101 = 29 <- published once, reused for years
— — — — —
To sign with leaf 2, reveal L2=54 plus its authentication path: sibling L1=31 and sibling Node34=69
Verifier recomputes Node12' = h2(31, 54) = 64 -> Root' = h2(64, 69) = 29 ✓ matches published root
This is literally XMSS: many one-time key pairs, one durable public key, a logarithmic-size authentication path per signature.
The trade Ethereum is actually making BLS signatures are 96 bytes and aggregate natively — 500,000 validators' signatures collapse into one 96-byte blob for free, which is why Ethereum's consensus is affordable to verify. Hash-based signatures like leanSig have no such native aggregation, and each individual signature runs to several kilobytes. That gap is exactly what leanVM exists to close.
05 — Closing the aggregation gap hash-based

leanVM: a minimal zkVM that does BLS's old job

leanVM is a small, purpose-built virtual machine designed specifically to be provable inside a ZK-STARK. Its job is narrow on purpose: check a batch of leanSig/XMSS signatures and produce one compact STARK proof attesting "every signature I checked was valid for this attestation." That proof — not the raw signatures — is what gets broadcast and stored, restoring the constant-size aggregation BLS used to give away for free.

Mechanically, this is Section 03's FRI folding applied to a very specific computation: the leanVM's own execution trace of verifying, say, 1,000 hash-chain signatures becomes the polynomial whose low-degree-ness gets proven via exactly the fold-and-spot-check process worked out above. Current research implementations build this on Plonky3 (a STARK proving framework) with WHIR as the polynomial commitment layer — both hash-based, no elliptic curves anywhere in the stack.

The trade is explicit: leanVM spends proving computation to buy back the compression that BLS got from elliptic-curve math. It's supported by a companion executable spec, leanSpec (written in Python, so the protocol's exact behavior is unambiguous), and a dedicated Protocol Snarkification research effort — a three-year, roughly $20M initiative formally verifying the cryptographic components this aggregation depends on. Roughly ten client teams are already running Rust implementations of leanSig today, well ahead of any mainnet deployment.

06 — Where this actually lands

The migration plan

Ethereum isn't picking one post-quantum scheme and hard-forking everything at once. The stated approach is cryptographic agility: upgrade each layer independently, keep multiple candidate schemes alive, and avoid locking the protocol into an assumption that might itself turn out to be wrong.

MilestoneFocusLayer(s)
IPost-quantum key registryConsensus
JPost-quantum signature precompilesExecution
LPQ attestations, real-time proofs, leanVMConsensus + Data
MPQ aggregation, PQ blobsExecution + Data
FutureFull PQ consensus & transactionsAll layers

L1 protocol upgrades are targeted, tentatively, for around 2029 — with full execution-layer migration (every wallet, every contract) extending years past that. The letters mark ordering, not fixed dates; this is an active research roadmap, not a shipped spec.

Three layers, three different jobs

  • Execution layer — ordinary accounts migrate via account abstraction: a smart account can swap in a new signature-verification scheme (candidates include Falcon, Dilithium, and SPHINCS+) without needing a protocol-wide hard fork per account.
  • Consensus layer — validators move to leanXMSS/leanSig signatures, aggregated through leanVM, exactly as described in Sections 04–05.
  • Data layer — blob commitments (Section 02) eventually need a hash-based successor to KZG for long-term data-availability security.

Risk isn't evenly distributed

Not every key matters equally the day quantum computers arrive. Roughly in order of urgency:

  1. User accounts (EOAs) that have already exposed a public key by transacting.
  2. Operational keys at exchanges, bridges, and custodians — high-value, high-exposure, frequently used.
  3. Governance and upgrade keys controlling protocol multisigs.
  4. Validator keys — lower urgency than it sounds, since consensus safety depends on breaking many keys simultaneously within a live, monitored network, not one key in isolation.

Rollups and L2s carry their own version of this list: sequencer and admin keys, cross-chain bridge contracts, user accounts (again via account abstraction), and — for zk-rollups specifically — the proof system itself, if it's SNARK-based and therefore inherits the same elliptic-curve exposure as KZG.

07 — Loose ends

Frequently asked

Does a quantum computer let someone steal ETH already sitting in my wallet?
Only if your wallet's public key has already been exposed on-chain (i.e., you've sent at least one transaction) and only once such a computer actually exists — which isn't yet the case. If your address has never transacted, only a hash of your public key is public, and hashes don't hand Shor's algorithm anything to work with.
Isn't "harvest now, decrypt later" a reason to worry about old transactions?
That phrase describes encrypted data being captured today for decryption later — a confidentiality problem. Blockchain transactions are already public; there's nothing confidential to harvest. The actual risk is entirely forward-looking: forging a new signature for funds under a key that becomes crackable in the future.
Why not just switch to a post-quantum scheme right now?
Because the field is still settling. Falcon, Dilithium, SPHINCS+, and hash-based schemes like leanSig each make different size/speed/statefulness trade-offs, and none has the multi-decade track record ECDSA has. Account abstraction and layer-by-layer migration let Ethereum swap schemes as the research matures, instead of locking in today's best guess.
What happens to lost or dormant wallets that can never be "migrated"?
This is a governance question, not a cryptography one. Ethereum's estimated dormant, key-unexposed supply is around 0.1% — small enough that it's a policy debate about legacy funds, not a protocol-breaking technical gap.
Is any of this open to outside review?
Yes — all of it is developed in the open under the leanEthereum GitHub organization: specifications (leanSpec), reference implementations (leanSig, leanVM), and the formal-verification work under the Protocol Snarkification initiative.
